# Commercial model

Read this reference when defining customers, positioning, packaging, pricing, revenue, or unit economics.

## Customer model

Define the narrowest primary segment that has all four:

- a frequent or costly problem;
- a reachable buyer;
- authority and budget to pay;
- a product-shaped solution that can be delivered repeatedly.

Capture:

| Field | Required decision |
| --- | --- |
| Primary ICP | Industry or use case, company/user size, geography, technical maturity |
| Trigger | Event that makes the problem urgent now |
| User | Person operating the product |
| Buyer | Person controlling budget |
| Alternatives | Manual work, incumbent, internal build, doing nothing |
| Switching barrier | Data, workflow, trust, integration, contract, or habit |
| Proof required | Demo, benchmark, trial, security review, reference, ROI evidence |

Do not use personas built mainly from demographics. Use behavior, constraints, purchase triggers, and decision criteria.

## Positioning

Express the positioning in this structure:

> For [primary customer] who struggles with [urgent problem], [product] is a [category] that produces [measurable outcome]. Unlike [main alternative], it [defensible difference].

Test that the statement is specific enough to exclude unsuitable customers. A positioning statement that fits any competitor is unfinished.

## Revenue-model selection

Choose based on how value accumulates:

| Value pattern | Likely model | Watch for |
| --- | --- | --- |
| Ongoing access or workflow | Subscription | Seat sharing, dormant accounts, churn |
| Variable consumption | Usage-based | Bill shock, metering disputes, volatile margin |
| Teams gaining value together | Per-seat or active-seat | Guest users, seasonal seats, role differences |
| Business outcome or transaction | Transaction or outcome fee | Attribution, refunds, regulatory exposure |
| High setup plus ongoing value | Setup fee + recurring subscription | Services margin and implementation capacity |
| One-off result | Project, license, or credits | Do not force recurring billing |

Hybrid pricing is justified only when each component maps to a distinct source of customer value or provider cost.

## Value metric

A good value metric:

- rises as the customer receives more value;
- can be measured and explained;
- is difficult to game;
- does not create fear during normal use;
- maintains acceptable gross margin.

Reject metrics chosen only because they are easy to count.

## Packaging

Use three tiers only when segments have meaningfully different needs. Do not create tiers by randomly withholding basic usability.

For each tier define:

- target customer and buying stage;
- included outcome and primary use case;
- value metric allowance;
- feature or governance boundaries;
- service level and support;
- overage or upgrade rule;
- disqualifying use cases.

Keep security and compliance features in higher tiers only when they create real incremental operating cost or enterprise value. Do not compromise baseline security for lower tiers.

## Pricing process

1. Estimate a price corridor from customer value, alternatives, direct cost, and relevant comparables.
2. Select a test price inside the corridor.
3. Define the proof mechanism: paid pilot, refundable deposit, checkout test, sales calls, or price-page experiment.
4. Set a decision threshold before testing.
5. Record what would cause a price, package, or segment change.

Avoid copying a competitor's number without matching buyer, bundle, usage, geography, and sales motion.

## Discounts and trials

- Prefer a time-bound trial when users can reach value without human setup.
- Prefer a guided proof or paid pilot when trust, integration, or implementation dominates.
- Use annual discounts to exchange price for commitment and cash-flow value, not by habit.
- Define discount authority, maximum discount, duration, renewal behavior, and whether discounts stack.
- Never offer an unlimited free tier when marginal cost or abuse risk is material without explicit controls.

## Commercial validation questions

- Can the buyer explain the paid outcome in one sentence?
- Does each tier have a distinct buyer or expansion trigger?
- Can entitlements enforce what pricing promises?
- Does the price survive realistic payment, infrastructure, support, fraud, and refund costs?
- Is expansion driven by more value rather than artificial inconvenience?
